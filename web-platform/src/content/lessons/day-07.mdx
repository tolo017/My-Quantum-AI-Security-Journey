# Day 7: Hashing & Public Key Infrastructure (PKI)

Cryptography ensures confidentiality, but it does not guarantee **integrity** (ensuring data has not been modified) or **authenticity** (proving who sent the data). To solve these two problems, we use cryptographic hashes and Public Key Infrastructure (PKI).

Today, we dive into hash functions, digital signatures, trust frameworks, and how to configure a custom Root Certificate Authority (CA) using OpenSSL.

---

## 1. Cryptographic Hash Functions

A hash function takes an arbitrary-sized input and maps it to a fixed-size string of characters (the hash/digest). Hash functions are **one-way operations**—you cannot reverse a hash back to its original input.

```
"Hello world" -------> [ SHA-256 Hash Function ] -------> a591a6d40bf42040... (64 chars)
```

### Essential Properties of Cryptographic Hashes:
1. **Deterministic:** The same input will always produce the exact same output.
2. **Pre-image Resistance:** Given a hash `H`, it is computationally impossible to find the input message `m` such that `Hash(m) = H` (One-way property).
3. **Collision Resistance:** It is computationally impossible to find two different inputs that produce the exact same output hash (`Hash(m1) = Hash(m2)`). MD5 and SHA-1 are broken because collisions can be generated in a short amount of time. Modern systems use **SHA-256** or **SHA-3**.
4. **Avalanche Effect:** A tiny change in the input (e.g., changing a single bit) must completely and randomly change the resulting output hash.

---

## 2. Digital Signatures

Digital Signatures provide **Integrity**, **Authentication**, and **Non-repudiation** (proving the sender cannot deny sending the message).

They operate on an inverted asymmetric keypair logic:
- **Signing:** The sender hashes the message, encrypts the hash with their **Private Key** (this is the Signature), and sends it along with the plaintext message.
- **Verification:** The receiver decrypts the signature using the sender's **Public Key** to reveal the original hash. They then hash the received message themselves and compare the two hashes. If they match, the integrity and sender identity are verified!

```
 Sender: [Message] ---> Hash ---> [Encrypt with PRIVATE key] ---> [Signature]
                                                                        |
 Receiver: [Message] ---> Hash == [Decrypt Signature with PUBLIC key] --+
```

---

## 3. Public Key Infrastructure (PKI)

How can you trust that a public key actually belongs to the person or website claiming to own it? If an attacker intercepts your connection and gives you their public key, they can decrypt your traffic (Man-In-The-Middle attack).

To solve this, we use **PKI (Public Key Infrastructure)**:
- **Certificate Authority (CA):** Trusted third-party organizations (e.g., Let's Encrypt, DigiCert) that verify the ownership of domain names and issue **Digital Certificates** (X.509 format).
- **Digital Certificates:** Contain the website's public key, domain info, and the digital signature of the trusted CA.
- **Root Certificates:** Operating systems and web browsers come pre-installed with the public keys of trusted CAs, allowing them to automatically verify the signature on any website's certificate.

## 4. Field Portfolio Project: Custom OpenSSL Root CA & Wildcard Signer

In high-security enterprise environments, security engineers configure private PKIs to secure internal server-to-server and API communications. We will build a complete Root CA using OpenSSL and sign a custom web service certificate.

### Step 1: Create Your PKI Workspace Directory
```bash
mkdir -p ~/beba_pki/root_ca
cd ~/beba_pki/root_ca
```

### Step 2: Generate the Root CA Private Key & Self-Signed Certificate
We will generate a secure, password-protected 4096-bit RSA Private Key for our Root CA, followed by a Root Certificate valid for 10 years:
```bash
# Generate Root CA Private Key
openssl genrsa -aes256 -out rootCA.key 4096

# Generate Root Certificate
openssl req -x509 -new -nodes -key rootCA.key -sha256 -days 3650 -out rootCA.pem \
  -subj "/C=US/ST=State/L=City/O=BebaCyberLabs/CN=BebaRootCA"
```

### Step 3: Sign a Custom Server Certificate
Now, let's generate a private key and a Certificate Signing Request (CSR) for a mock internal application server `intranet.bebalabs.local`:
```bash
# Generate Server Key
openssl genrsa -out server.key 2048

# Generate Server CSR
openssl req -new -key server.key -out server.csr \
  -subj "/C=US/ST=State/L=City/O=BebaCyberLabs/CN=intranet.bebalabs.local"

# Sign the Server CSR using our custom Root CA Certificate
openssl x509 -req -in server.csr -CA rootCA.pem -CAkey rootCA.key -CAcreateserial \
  -out server.crt -days 365 -sha256
```

This completes the generation of your secure private PKI suite! You can present these certificate configurations in cloud infrastructure design portfolios.

## 5. Hands-On Lab: Calculating Hash Integrity on Zorin OS

Let's calculate the hash of a file to verify its integrity:

```bash
# 1. Create a file
echo "Audit Log: Event #1828" > audit.log

# 2. Generate a SHA-256 hash of the file
sha256sum audit.log
# Output: 5f93976eb71df6c87df34a5d...

# 3. Modify the file slightly (change a single character)
echo "Audit Log: Event #1829" > audit.log

# 4. Check the SHA-256 hash again
sha256sum audit.log
# Notice how the output hash has completely changed! (Avalanche Effect)
```
