# Day 5: Virtualization, Container Escapes & Custom Lab Networks

In offensive security and malware analysis, you will run malicious code and vulnerable systems. If your laboratory isn't perfectly isolated, an exploit can escape onto your local host network, putting your personal files and devices at risk.

Today, we dive into virtualization hypervisors, container breakouts, privileged capabilities, and advanced network sandboxing.

---

## 1. Hypervisors vs. Container Virtualization

To isolate resources, we use two main forms of virtualization:

```
+-----------------------------------+   +-----------------------------------+
|         HYPERVISOR (VM)           |   |         CONTAINER DOCKER          |
+-----------------------------------+   +-----------------------------------+
| [App A] [App B] | [App C]         |   | [App A]   [App B]   [App C]       |
| [Guest OS]      | [Guest OS]      |   | [Bins/Libs] [Bins/Libs] [Bins/Li] |
| [Hypervisor Engine (Type 1 or 2)] |   | [Docker Daemon (Engine)]          |
| [Host Operating System]           |   | [Host OS (Shared Kernel Space)]   |
+-----------------------------------+   +-----------------------------------+
```

### Type-1 & Type-2 Hypervisors (Virtual Machines)
- **Type-1 (Bare Metal):** Runs directly on the system's hardware (e.g., Proxmox, ESXi). It is highly performant and secure, making it ideal for servers.
- **Type-2 (Hosted):** Runs as an application on a host OS (e.g., VirtualBox, VMware Workstation). It virtualizes every single hardware component (virtual CPU, RAM, disk, NIC), resulting in high resource overhead.

### Containerization (Docker)
Docker does not virtualize hardware. Instead, containers run as isolated processes sharing the host operating system's kernel. This is made possible by three Linux core features:
1. **Namespaces (Isolates what you can see):** Limits access to processes (`pid`), network configurations (`net`), mount paths (`mnt`), and users (`user`).
2. **Control Groups / cgroups (Isolates what you can use):** Controls resource consumption (limiting RAM, CPU cores, swap file sizes, and I/O speeds).
3. **Union File System / UnionFS (Isolates storage):** Layered file system where changes are made in a temporary, top-level write layer, keeping base operating system images unmodified.

### Container Escape Security Risks
Because containers share the host's operating system kernel, running a container with the `--privileged` flag or adding raw kernel capabilities (like `--cap-add=SYS_ADMIN`) completely breaks this boundary. If an attacker gains code execution in a privileged container, they can mount the host's `/dev/sda1` drive and execute commands directly on the host computer, completely escaping the sandbox!

## 2. Dynamic Networking: Isolated Docker Bridges

When analyzing vulnerable containers, you must place them in an isolated bridge network to prevent them from communicating with your local Zorin host or physical home router.

```
                  [ Physical Home Router / WAN ]
                                ^
                                | (NAT)
                    [ host0 Interface / Zorin ]
                                ^
                                |
                  +-------------v---------------+
                  |  Docker Isolated Bridge Net |
                  +------+---------------+------+
                         |               |
                         v               v
                   [Kali Container] [Target App Container]
```

By default, Docker places containers in the shared `bridge` network. For complete isolation, we create custom network bridges:
```bash
# Create an isolated local subnet bridge
docker network create --driver bridge --subnet=10.99.0.0/24 secure_cyber_range
```

## 3. Field Portfolio Project: Multi-Subnet Hardened Environment

In enterprise cloud security, you must implement **Defense in Depth** by segmenting services into multi-tiered subnets. Let's build a hardened multi-subnet production architecture containing:
1. A **Web Frontend** subnet accessible via specific ports.
2. An **Isolated Database** subnet with zero external network connectivity.

### Step 1: Create a Lab Directory
```bash
mkdir -p ~/beba_isolated_network
cd ~/beba_isolated_network
```

### Step 2: Configure the Subnets (`docker-compose.yml`)
Create a `docker-compose.yml` that establishes strict subnet segmentation:
```yaml
version: '3.8'

services:
  web_frontend:
    image: nginx:alpine
    container_name: web_service
    ports:
      - "8080:80"
    networks:
      - frontend_net
      - backend_net
    security_opt:
      - no-new-privileges:true
    read_only: true
    tmpfs:
      - /var/cache/nginx
      - /var/run

  database_backend:
    image: redis:alpine
    container_name: db_service
    networks:
      - backend_net
    deploy:
      resources:
        limits:
          cpus: '0.2'
          memory: 256M

networks:
  frontend_net:
    driver: bridge
    ipam:
      config:
        - subnet: 172.50.1.0/24
  backend_net:
    driver: bridge
    internal: true # Totally isolated from the external host and WAN
    ipam:
      config:
        - subnet: 172.50.2.0/24
```

### Step 3: Run and Verify Isolation
```bash
docker-compose up -d

# Verify database_backend cannot contact the external world (should return timeout/fail)
docker exec -it db_service ping -c 2 google.com
```

This ensures that even if an attacker compromises the Nginx web container, they cannot access your host network or resolve external internet targets.

## 4. Hands-On Lab: Isolating a Targeted Container

Let's launch an isolated container attached specifically to our customized local network range:

```bash
# 1. Spin up an alpine linux container in our secure bridge range
docker run -it --rm --network=secure_cyber_range --name target_host alpine sh

# 2. Inside the container shell, verify its local IP configuration
ip addr show
```

The container will receive a secure IP address inside the `10.99.0.x` range, completely segmented from your host machine's home network!
